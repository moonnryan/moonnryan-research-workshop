# 多平台模型任务的版本与产物管理

训练、模型编译和推理服务可以共用任务管理方式，但每一步交给工具链的内容不同。训练需要固定数据、初始化与优化配置，编译需要表达目标芯片、shape 和精度，运行时则按最终产物接口加载与送数。

统一平台需要保存这些差异，同时让任务能够独立复现。只把命令包装成同一个入口，仍可能出现参数被忽略、版本不明，或者文件生成成功却无法在目标设备使用的问题。

# 一、任务入口与设备执行分开

插件负责把公共请求转换成工具链配置，worker 负责设备资源、进程生命周期、日志与状态。独立命令行和平台入口调用同一份计划生成逻辑，减少两套配置逐渐分叉。

```text
任务参数与资源引用
    → 插件生成计划并校验
    → 固定镜像与设备 runner 执行
    → 检查结果并整理产物
```

训练插件可以选择检测训练仓库或 LLaMA-Factory，编译插件可以选择 BModel、OM、TensorRT、RKNN 等后端。worker 不需要了解每个模型的全部参数，也不能替插件决定不支持的选项如何处理。

任务目录保存配置快照、日志、状态与产物引用。数据和基础权重按只读路径或明确资源标识引用，缓存按内容及参数哈希生成，避免每次复制整份媒体或重复分词。已指定自定义权重时，不应悄悄下载另一个同名模型作为替代。

# 二、公共参数需要对应实际能力

统一名称不代表各后端拥有相同能力。参数校验要在执行前完成，无法支持时明确拒绝，不能接收后忽略。

| 参数或条件 | 公共含义 | 需要保留的差异 |
| --- | --- | --- |
| 权重与初始化 | 指定模型起点 | 原始权重、微调与恢复训练不是同一模式 |
| 数据与前处理 | 指定实际输入 | 标签格式、归一化与校准前处理按模型确定 |
| input_shape | 输入张量形状 | 动态支持按模型、后端和版本声明 |
| precision | 目标精度意图 | 名称相同不保证每层或 I/O 精度相同 |
| target | 目标设备或编译目标 | TensorRT 的 GPU 与 RKNN 的 target_platform 语义不同 |
| calibration | 校准数据与流程 | 入口、范围来源和数值变换按后端确定 |
| 输出 | 保存本次任务结果 | checkpoint、平台模型与附属文件分别描述 |

镜像和插件分别维护：一个环境底座可以运行多个插件，一个插件也可以有 CUDA、ROCm 或 CANN 等底座。设备资源选择与模型配置不应互相隐式覆盖。

# 三、记录能够复现任务的版本组合

| 维度 | 记录项 |
| --- | --- |
| 设备与系统栈 | 实际设备、驱动、CUDA/CANN/ROCm |
| 框架与工具链 | torch、torch_npu、transformers、训练或转换仓库 commit |
| 数据与模型 | 数据版本、划分、权重哈希、类别与前处理 |
| 配置与补丁 | 最终配置、等价改写、后端守卫与可关闭开关 |
| 执行环境 | 镜像 digest、挂载代码与资源路径 |
| 验证状态 | 未验证、冒烟通过、完整任务通过及其条件 |

浮动 latest 或 nightly 无法完整表达经过验证的组合。镜像之外若还有挂载代码和工具补丁，也要记录对应版本。相同模型文件名不足以证明两次训练或编译的起点相同。

# 四、任务已提交与模型已就绪是不同状态

服务发现、任务提交、日志与升级属于控制面，权重加载与推理属于执行面。接口返回“启动任务已提交”时，模型可能还在加载，需要显式区分：

```text
STOPPED → STARTING → READY
             ↓
           FAILED
READY → STOPPING → STOPPED
```

镜像按本地镜像、离线包、远程仓库的顺序解析后，核验最终 digest。加载完成、接口可用和任务结果正确也应分别验证，不能仅凭进程存在就进入 READY。

# 五、产物通过验证后再更新正式版本

编译流程包含输入校验、导出与图检查、后端编译、目标设备重加载、数值和任务验证。临时目录与正式输出分开；失败时保留诊断材料，继续使用旧产物，避免先覆盖文件再发现新模型不可用。

训练任务保存配置、指标和 checkpoint 语义，编译任务保存源模型与部署接口，运行时根据同一份清单加载。manifest 至少包含哈希、I/O、前处理执行位置、目标、版本、精度和测量条件；拆分模型与附属权重作为同一版本发布。

“生成文件”“设备加载成功”“数值通过”与“任务效果通过”是不同层次。只记录产物扩展名或一个成功状态，无法判断两个同名模型是否可以互换。

# 六、跨平台性能先拆分阶段

归档 CV 三平台测试中，AMD 的训练迭代与 GPU 接近，总时长差异集中在未启用 AMP 的验证。验证加入 no_grad 与明确的混合精度后，10 epoch 总时长约从 260 多秒降到 120 多秒，而任务 AP 保持接近。整任务时间改善不能全部归为训练 kernel 提速。

Ascend 的 DataLoader 曾在 fork 后继承线程锁而死锁，改用 forkserver 后恢复。需要同时检查启动方式、worker 数、缓存和第三方库线程；worker 越多并不一定越快。

AMP 验证与后端执行模式按可选配置启用，并进行 AP 回归。图模式遇到空张量或 capture 限制时保留 eager 基线，不把实验路径直接设为默认。

训练迭代、数据加载、验证和保存分别计时；推理也分别统计前处理、执行、搬运和后处理。分词缓存、验证 AMP 与算子改写作用于不同阶段，需要在固定输入和计时范围下比较。

# 七、一些反思

统一任务管理的价值，是让一次执行的条件与结果能够被解释。训练、编译和服务运行不需要强行拥有相同配置，但应能追溯同一模型使用了什么数据、工具链和验证结果。

稳定的任务记录与变化的后端实现分开维护，升级工具链时才有机会保留相同输入和参考结果。明确报告未验证、不支持和已经通过的组合，比一个始终返回成功的包装入口更有用。
