# NVIDIA GPU 负载下整机掉电的分层排查

vLLM 在编译或 autotune 阶段失联，首先要确认故障范围：引擎退出、容器退出、操作系统重启，还是整机异常下电。SSH 断开只说明入口失联，不能独立证明掉电，更不能直接归因于 OOM。

双张 RTX 6000D 的归档排查中，系统存在异常启动周期，BMC SEL 记录了 5V 电源轨异常下电与 PCIe Riser 告警。此时需要转向硬件层验证。

# 一、建立时间线

```bash
last -x
journalctl --list-boots
journalctl -k -b -1
nvidia-smi
nvidia-smi topo -m
```

同时取得 BMC SEL 和电源、Riser、线缆状态。OS 日志在突然下电时可能来不及写入，缺少 Xid 或 OOM 并不等于硬件正常。公开记录仅保留故障类别，省去管理地址、序列号与机房信息。

# 二、拓扑与供电分别判断

双卡之间为 SYS，说明通信经过跨 socket 路径。它可能增加 TP 通信成本，但正常拓扑慢不应直接等同于掉电。

额定双电源总容量不足以排除供电问题。冗余模式、某条电源轨、Riser 接触和线缆，都可能产生局部异常。SEL 告警支持硬件排查，尚不能判定哪一件器件损坏。

# 三、控制复现负载

| 步骤 | 目的 |
| --- | --- |
| 关闭异常容器自动重启 | 防止系统恢复后反复触发 |
| 单卡、基础精度路径 | 减少通信与新 kernel 变量 |
| 固定短输入与并发 | 排除容量变化 |
| 分别开启 KV 量化、MTP、图模式 | 检查组合稳定性 |
| 稳定后再双卡 TP | 单独测试跨卡路径 |

单卡分别开启 MTP 或低位 KV cache 曾通过，同时开启则不稳定。这与整机下电的硬件告警是两条需要分别验证的线索，不能把一个解释为另一个的已证明原因。

# 四、恢复后的验证范围

维修或重新接线后，分别测试单卡持续计算、双卡同时负载和跨卡通信，记录功耗曲线与 SEL。即使降低 power limit 后不再掉电，也只能说明降低负载改变了触发条件，不能独立证明额定电源容量不足。

如果问题只在某个 autotune kernel 触发，固定驱动、模型和输入，逐级恢复对应路径。若机器不再下电但引擎仍退出，应回到软件阶段继续排查，避免把“硬件修复完成”当成整个服务已验收。

最终报告分别列出已消失的症状、仍存在的错误与完成的长测。整机失联、GPU fault 和模型输出异常可以同时存在，却不必共享同一个原因。

# 五、一些反思

进程错误看服务日志，设备错误看驱动与 kernel，整机下电还要看带外管理。在错误层继续调参会增加复现次数，却不能排除真正问题。

已经出现电源轨异常时，先处理硬件健康，再逐级恢复负载。保留相同测试配置，才能判断维修后问题是否消失。
