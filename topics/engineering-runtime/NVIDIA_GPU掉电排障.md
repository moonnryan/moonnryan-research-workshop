# NVIDIA GPU 负载下整机掉电的分层排查

双卡推理在模型加载后进入编译、图捕获或 autotune，随后 SSH 断开，很容易被当成显存不足或某个 kernel 崩溃。但 SSH 只反映访问链路的状态，不能独立证明机器掉电。排查首先要确认故障发生在哪一层，再判断最后一条日志与故障之间是什么关系。

一组双卡高功耗 NVIDIA GPU 的排查记录中，同时出现过整机异常下电、双卡引擎初始化卡住，以及单卡优化组合不稳定。BMC 后续记录到 5V 相关 PwrOk 信号丢失和 PCIe 转接板管理异常；另一组较小模型的双卡测试又能正常返回请求。这些现象需要分别解释，不能用一次成功启动覆盖硬件告警，也不能把全部软件异常都归到电源。

# 一、先确定故障范围

| 现象 | 首先检查 | 目前能够说明什么 |
| --- | --- | --- |
| API 不可用，SSH 正常 | 服务日志、端口、容器状态 | 服务尚未 ready、退出或阻塞 |
| 容器退出，系统启动周期未变 | 退出状态、OOM、信号与驱动日志 | 故障至少影响应用或容器 |
| SSH 失联，BMC 显示主机仍开机 | 网络、系统响应、带外控制台 | 可能是网络故障或系统卡死 |
| 出现新的 boot ID | 上一启动周期日志与 BMC 事件 | 系统发生过重启，原因仍需核对 |
| BMC 记录异常下电与电源信号丢失 | SEL、传感器、主板与供电路径 | 已有独立于应用日志的硬件侧证据 |

外部代理端口返回 connection refused，只能说明那个入口不可用；它可能随主机重启而退出，也可能单独故障。不能据此排除网络问题。

容器退出码 137 表示进程收到 SIGKILL，并不自动等于 OOM。应结合 `OOMKilled`、cgroup/内核日志和当时的管理操作判断。默认 OOM 处理通常杀进程，但 `panic_on_oom`、watchdog 等策略也可能把内存故障升级为系统重启，因此“重启了，所以绝不可能是 OOM”同样过早。

# 二、把容器、操作系统与 BMC 放在同一条时间线上

## 2.1 先保留启动周期与容器现场

恢复访问后先查询，不立即重启容器覆盖现场：

```bash
date -Is
timedatectl status
uptime -s
last -x -n 20
journalctl --list-boots --no-pager
```

`last -x` 中的 crash 与短启动周期能提示上次会话非正常结束，但不是供电故障的单独证明。结合实际故障时间选择 boot ID，不默认 `-b -1` 就是要找的那次启动：

```bash
BOOT_ID='<从 list-boots 中选择的故障启动 ID>'
journalctl --boot="$BOOT_ID" -k -o short-iso-precise --no-pager
journalctl --boot="$BOOT_ID" -u docker -o short-iso-precise --no-pager
```

再检查对应容器，名称使用实际值：

```bash
CONTAINER=inference-test
docker inspect --format '{{json .State}}' "$CONTAINER"
docker inspect --format '{{.RestartCount}} {{json .HostConfig.RestartPolicy}}' "$CONTAINER"
docker logs --timestamps --tail 3000 "$CONTAINER"
```

`inspect` 反映当前可见的状态，并不是跨重启的完整历史。自动重启、容器重建或删除后，旧退出状态可能已经丢失；需要同时保留应用日志、Docker 日志和启动周期。

内核日志重点搜索 OOM、Xid、PCIe AER、热保护与 watchdog：

```bash
journalctl --boot="$BOOT_ID" -k --no-pager \
  | grep -Ei 'out of memory|oom-kill|killed process|NVRM|Xid|AER|PCIe|thermal|watchdog|panic'
sysctl vm.panic_on_oom kernel.panic kernel.panic_on_oops
```

突然断电时，最后一段 journal 可能没来得及落盘；没有匹配结果，只能说明已保存日志中未找到相关记录。如果系统未保留历史 journal，也不能把查询不到上一启动周期理解为没有异常。

## 2.2 BMC 证据独立采集

优先导出 BMC 的系统事件日志、当前传感器、硬件清单和电源状态。已经具备本地 IPMI 工具时，可以查询：

```bash
ipmitool sel time get
ipmitool sel elist
ipmitool sdr elist
ipmitool chassis status
```

工具未安装时直接使用 BMC Web 导出，不必为了收集证据先改变故障机器的软件环境。原始日志保留在受控位置，公开文章只保留事件类型和先后关系，不附管理地址、FRU 编码、序列号或原始 dump。

核对 BMC 与 OS 时区及时间偏差后，再组织证据：

| 相对阶段 | 应用与 OS | BMC |
| --- | --- | --- |
| 进入高负载路径 | 编译、warmup 或 GEMM autotune | 观察功耗与硬件事件 |
| 入口失联 | 日志中断，SSH 不可达 | 是否记录主机电源状态变化 |
| 恢复访问 | 新 boot ID，容器可能自动启动 | 异常下电、恢复供电或人工启动事件 |
| 稳态检查 | GPU 可见、空闲查询正常 | 哪些告警仍然存在 |

`ACPI soft-off` 描述电源状态，`restarted by command` 可能是恢复动作；应与前面的故障事件分开，不能把日志中的最后一个启动动作当成最初原因。

# 三、从硬件记录缩小范围

这组记录中，最有价值的证据来自三个层次：

| 证据 | 能支持的判断 | 仍不能推出 |
| --- | --- | --- |
| 多次异常下电伴随 `PwrOk Sig. Drop`，对象为 5V 相关信号 | 需要优先检查局部供电、主板与相关板卡路径 | 已确定是哪一个元件失效 |
| PCIe 转接板温度不可读、EEPROM/I2C 访问反复失败 | 转接板及其管理、连接链路存在异常线索 | 温度必然过高或转接板必然损坏 |
| 采集时 PSU 在位、部分电压读数正常 | 稳态查询没有显示这些项目持续异常 | 负载切换瞬间没有压降或保护动作 |

转接板管理异常跨越多个启动周期，部分记录早于本次推理故障。它提示存在较长期的硬件问题，但不能仅凭时间接近就断言 I2C 读取失败导致了下电。更强的关联来自异常下电时的电源信号事件、主机电源丢失记录，以及维修后的同条件复测。

5V 相关 PwrOk 信号丢失也不是示波器捕获到的完整电压波形。BMC 描述的是被监测状态，具体涉及电源模块、主板电路、转接板还是连接件，需要结合厂商原理与交叉测试定位。

电源预算还要考虑冗余模式。两只 PSU 的铭牌功率不能直接相加后当作整机可用预算；N+N 冗余、输入条件和平台功耗策略可能改变可用容量。即使总容量足够，局部供电、接触或线缆问题仍可能触发异常。

GPU 在重启后能正常枚举、ECC 错误计数为零，也不能覆盖 PCIe、供电和瞬态稳定性。空闲状态与模型加载阶段的低功耗快照，更不能代替故障瞬间的测量。

# 四、把拓扑、卡住和掉电分开判断

## 4.1 SYS 是通信路径信息

`nvidia-smi topo -m` 中的 `SYS` 表示设备间通信经过 PCIe 以及跨 NUMA 节点的处理器互联路径。它不是 NVLink，也不能单凭这一个标记确认 P2P 实际使用方式、通信带宽或 NCCL 选择的算法。

```bash
nvidia-smi topo -m
nvidia-smi --query-gpu=index,pci.bus_id,pstate,temperature.gpu,utilization.gpu,memory.used,power.draw,power.limit \
  --format=csv
nvidia-smi -q -d POWER,ECC,TEMPERATURE
```

TP 会频繁触发跨卡通信，拓扑不理想可能增加等待和通信开销。它是排查通信路径的依据，但“通信较慢”不能直接解释电源保护。需要分别验证单卡计算、双卡独立计算和双卡通信。

## 4.2 卡在启动阶段不等于服务已经可用

另一组较小模型的双卡测试中，默认优化组合完成了部分编译与图捕获，随后反复提示：

```text
No available shared memory broadcast block found in 60 seconds
```

这条日志反映进程间广播等待，不能只按字面就归因为 Docker 的 /dev/shm 不够。卡住时 GPU 利用率很高，也不代表应用正在有效生成；应同时检查 worker/rank 日志、启动阶段和真实请求是否能够返回。

同一模型的配置对照为：

| 配置 | 已记录结果 | 证据意义 |
| --- | --- | --- |
| 默认 attention、自定义 all-reduce、编译与图捕获 | 初始化卡住，接口未就绪 | 存在优化路径稳定性问题 |
| 更换 attention、关闭自定义 all-reduce、使用 eager | 启动并完成请求 | 得到可用基线，但同时改变多项 |
| 恢复默认 attention 与编译/图捕获，仅关闭自定义 all-reduce | 启动并完成请求 | 排查重点缩小到自定义通信路径及其交互 |

最后一组结果说明，在该模型与软件栈中，默认 attention 和图模式并非必然失败。自定义 all-reduce 是优先回归的变量，但还需要恢复开关后重复测试、固定其他条件，才能进一步确认稳定复现关系。

这组成功请求证明了当时那条 TP=2 路径可用，不能外推为高负载硬件完全健康，更不能解释另一条整机异常下电记录。

## 4.3 单卡组合失败是第三条线索

单卡记录还显示：MTP 与某种 4 bit KV cache 路径分别启用可以运行，同时启用不稳定。它说明问题不完全依赖双卡拓扑，却不证明两个功能在所有版本上都不兼容。

权重量化、KV cache 量化与 speculative decoding 分别改变不同计算和状态路径。回归时记录具体实现、版本和生效日志，不仅记录命令行中是否出现了一个参数。

# 五、控制复现负载，而不是反复触发下电

出现明确电源信号或板卡告警后，先保存证据并暂停反复复现。自动重启策略可能让主机恢复后立即再次进入同一高负载路径。维护时可对实际故障容器执行：

```bash
docker update --restart=no "$CONTAINER"
docker stop "$CONTAINER"
```

这是会改变服务状态的维护操作，不属于前面的只读采集。若容器由 Compose、systemd 或其他控制器创建，还要核对上层重建策略；仅修改一个容器不保证之后不会被重新拉起。

硬件健康检查完成后，按下面顺序设计复测，每一步记录设备、负载、持续时间、结果与 SEL：

| 测试 | 固定条件 | 用于区分 |
| --- | --- | --- |
| 两张 GPU 分别单卡运行 | 同一模型、输入与基础精度路径 | 问题是否跟随某张卡 |
| 双卡同时独立计算 | 不使用跨卡 TP，控制总负载 | 并行负载与供电、散热压力 |
| 双卡通信测试 | 固定版本、消息规模与循环次数 | PCIe、NUMA、通信库路径 |
| 小模型保守 TP=2 | 默认 KV、不启用 MTP、关闭自定义 all-reduce、eager | 软件双卡基础路径 |
| 逐项恢复优化 | 每次仅修改一项 | 特定 kernel、图模式或组合交互 |

合成压力测试与模型负载不是等价替代。普通压力测试也异常，能缩小到更基础的路径；普通压力测试通过，仍不能排除只在特定数据搬运、负载切换或 kernel 组合下出现的问题。

降低 GPU power limit 可以作为受控变量，但要在每次测试前查询实际限制，不能假设重启后仍然保持。persistence mode 也不等于保存所有功耗设置。降低限制后稳定，只说明改变负载后触发条件变化；仍然异常，也不能直接排除局部供电问题。常规功耗采样没有捕获到峰值，同样不能排除更短的瞬态。

如果模型无法在单卡容纳，选择适合的较小测试模型或单卡计算样例隔离硬件路径，不把模型容量失败误记为单卡硬件失败。

# 六、按单变量回归软件路径

先固定模型权重、容器镜像、驱动、框架、kernel 库、输入长度与并发，建立配置表。软件回归可以从以下两项开始建立保守通信基线：

```text
--disable-custom-all-reduce
--enforce-eager
```

对应 vLLM 版本需要从帮助与实际启动日志确认。eager 用于排除编译和图捕获影响，不会自动绕开底层 GEMM kernel 或其 autotune，因此 eager 下仍卡在 autotune，并不能说明该开关未生效。

后续逐项恢复图模式、自定义通信、attention 后端、KV 量化与 MTP。先测试单功能，再测试确实需要的组合；输入长度、并发和 batching 保持不变。不要同时换模型、升级镜像和调整多个开关，然后把成功归功于其中一个参数。

日志中某个 communicator 不支持设备能力时，要看它是否已回退到受支持路径；该提示本身不一定是致命错误。相同地，最后一条 `Tuning fp4_gemm` 只定位到故障附近的阶段，异步执行、日志缓冲和突然断电都可能让真正的触发点出现在它之后。

每组至少检查启动完成、实际请求返回、持续请求与资源是否稳定。仅有端口监听、模型列表或 GPU 高利用率，不构成完整服务验证。

# 七、维修后需要什么证据

由维护人员在断电和厂商流程下检查 GPU 辅助供电、PCIe 转接板、插槽与线缆。设备支持交叉替换时，记录 GPU、插槽、转接板与供电线的对应关系，每轮只改变一项：

- 故障跟随 GPU：进一步检查卡本体及其相关路径。
- 故障停留在同一槽位或转接板：优先检查该路径。
- 单卡均正常，双卡独立计算也异常：关注总负载与共享硬件。
- 仅跨卡通信或特定优化组合异常：继续检查通信和软件路径，同时保留硬件证据。

这些是定位方向，不是部件定责。多项一起重插后恢复，只能证明整组维护改变了条件，不能确认其中哪一项是原因。

维修前保存 SEL 和当前告警，维修后区分历史事件、恢复事件与新发生的告警，不用清空日志代替故障消除。重新运行相同测试矩阵，再逐步恢复原负载。最终记录清楚：

| 结论层次 | 需要说明 |
| --- | --- |
| 已确认 | 异常下电记录、重复出现的信号和可复查的配置差异 |
| 优先怀疑 | 转接板、管理链路、局部供电或自定义通信等候选 |
| 尚未完成 | 换件验证、开关恢复复测、长时间稳定性与故障恢复 |

归档材料足以支持把硬件供电与转接板链路列为整机下电的优先排查方向，也支持单独回归自定义 all-reduce 和优化组合。材料没有给出更换某个部件后完整复测通过的闭环，不能把排查建议改写成已经完成的维修结论。

# 八、一些反思

这类问题最容易混淆的是故障范围、触发负载与根因。应用日志说明程序推进到哪里，内核日志说明系统观察到了什么，BMC 则补充操作系统之外的电源与硬件事件。把这些证据对齐之后，才知道下一次测试应该改变哪一个条件。

软件上的可用配置与硬件健康需要分别确认。关闭自定义通信后能返回请求，是有价值的回退方案；电源信号与板卡告警是否消失，仍然需要独立验证。保留这种区分，才能避免一个局部成功掩盖另一个尚未闭环的问题。
